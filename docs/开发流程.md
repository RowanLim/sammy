# Sammy 开发流程

> 这份文档回答三件事：**在哪开发、用什么开发、怎么一步步执行。**

---

## 一、平台怎么分工

| 机器 | 角色 | 为什么 |
|:---|:---|:---|
| **Mac mini** | ⭐ **主开发机** | 产品是桌面宠物：透明浮窗、置顶、拖拽、那张脸 —— **看不见产品就没法开发它**。而且你的注意力在这台机器上 |
| **Linux（Nex，192.168.110.177）** | **并行开发机 + 常驻服务机** | 实测配置：20 核 / 31G 内存 / 346G 空闲 / Docker 活着 / **有声卡（含录音设备）** / `DISPLAY=:1` 有图形会话 / **Python 3.11.16（和我们同版本）**。它可以承担：语音链路常驻监听、MCP 服务、8 小时长跑稳定性测试、CI runner |
| **树莓派（待购）** | **只做移植验证**，不是开发机 | 性能弱、工具链麻烦、来回拷贝慢。开发中的每一天都不该在它上面 |
| 手机 / 平板 | 不做 | PRD 非目标 |

### ⭐ 一条比分工更重要的架构约束

> **任何没有界面的模块（大脑、记忆、工具、语音），都必须能在 Linux 上无头跑通。**

这条约束有两个好处：
1. 它逼我们**把逻辑和界面彻底解耦**（就是 py-xiaozhi 那种分层）—— 否则跨不了平台。
2. 它给了我们一个**天然的验收方式**：**能在 Nex 那台跑起来，就说明没耦合。**

所以以后写模块，先问一句：这个能 `ssh` 到 Linux 上跑吗？不能，就说明它偷了桌面的依赖。

## 三、日常开发循环

```
改代码  →  pre-commit 自动跑（ruff → 格式化 → 离线测试）  →  pytest 全量
      →  ./run.sh 或用眼睛看截图  →  提交（一个改动一个 commit）
```

### 三层测试，各有分工（别混用）

| 层 | 覆盖什么 | 耗时 | 什么时候跑 |
|:---|:---|:---|:---|
| **离线单测**<br>`pytest -m "not live"` | 情绪解析、记忆读写、渲染取景、窗口逻辑 —— 确定性、可断言 | **0.6s** | 每次提交（pre-commit 自动） |
| **联网验收**<br>`pytest -m live` | PRD 里**带数字的标准**：延迟预算、重启后还记得 | ~30s | 每次改了逻辑 |
| **真机自检**<br>`./run.sh --selftest` / `scripts/dev_check.py` | 真的出窗口、真的连大模型、全表情渲染 | 秒级 | 每轮 UI 改动 |

### 提交规范

- **一个改动一个 commit**，信息写清「为什么」而不只是「改了什么」
- 不用 `git commit --no-verify` 跳过钩子（钩子挂了说明代码真有问题）
- `docs/PRD.md` 是唯一事实来源：**想加功能，先改文档，再写代码**

## 四、验收纪律（血的教训）

1. **PRD 里每条需求都带可测标准** ——「感觉做完了」不算完成。
2. **单次采样不是验收。** 延迟这种有尾延迟的指标必须测**分布**（p50/p90/max）。
   实测同一个问题：最快 1.35s、最慢 3.09s —— 单次断言写 `latency < 3.0` 会变成随机挂的假测试。
3. **界面改动必须看截图。** 坐标系、透明度、裁切，任何一处错了屏幕上就是一团垃圾，**光看代码看不出来**。
4. **踩过的坑写进 `docs/DEVLOG.md`**，工程约定写进技能 —— 否则下次一定再踩一遍。

## 五、第一步（已完成）

**第一步 = 工程地基**，因为它决定后面所有开发的效率。地基不牢，功能写得越快越贵。

- ✅ **ruff**：检查 + 格式化，并针对中文项目调好规则（关掉全角标点误报）
- ✅ **pytest**：77 个离线用例 + 4 个联网验收，覆盖率 62%
- ✅ **pre-commit**：提交前自动跑，不过不让提交
- ✅ **`SammyWindow` 支持依赖注入** —— 可测试性不是测试的事，是设计的事

### ⚠️ 地基当天就抓到 3 个真 bug

| # | Bug | 后果 | 修法 |
|:-:|:---|:---|:---|
| 1 | 延迟断言用**单次采样** | 假验收：服务端抖一下就"失败"，会让人开始忽略测试 | 改成测分布（p90 进预算，单次不超 5s） |
| 2 | **记忆写入失败会把回复覆盖掉** | 用户明明拿到了答案，却看到"我卡住了" | 对话失败与记忆失败**分开兜** |
| 3 | `needs_nightly` 会重复整理当天 | 当天整理一次后，之后新增的记录**永远轮不到整理** | 改成优先补"已经过完但没整理"的日子 |

> 这三个都不是"写错一行"，而是**设计层面的漏洞** —— 只有真跑测试才会露出来。
